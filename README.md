# Vault laboratory: ICP-Brasil, PKI, and dynamic credentials

A small web application that shows three Vault workflows side by side:

- an **ICP-Brasil type A1 certificate** stored in KV: the leaf certificate, its public key, its private key, and the issuing CA certificate
- a **service TLS certificate** issued by the PKI secrets engine
- a **dynamic PostgreSQL role** from the database secrets engine

The application never logs in to Vault. Something else renders the secrets into files, and the process re-reads those files on each refresh.

| Runtime | How secrets arrive |
| --- | --- |
| Podman | Vault Agent, AppRole, shared volume |
| Nomad | Nomad's Vault template stanza (the same renderer as Vault Agent) |
| Kubernetes | Vault Secrets Operator and the Kubernetes auth method |

Vault itself is configured with Terraform.

## Laboratory boundary

Vault stores the ICP-Brasil certificate. It does not issue it. An accredited chain is signed by an intermediate AC (Serpro, Certisign, and the others), and that intermediate is signed by AC Raiz. Those private keys stay with the accredited authority. KV holds the already-issued leaf, the leaf keys, the issuing CA certificate, and the root certificate so the page can show the chain.

`deploy/icp/` is a laboratory stand-in with the same shape, generated by `deploy/icp/generate.py`. The issuer common names say **Demonstracao**. The policy id `2.16.76.1.2.1.99999` sits in the A1 arc so the profile is recognizable; `99999` is not an assignment from ITI. Replace those PEM files with an export from a real A1 certificate, then apply Terraform again. Leave the intermediate and root private keys out of KV.

DOC-ICP-04 type A1 is a software signature certificate: RSA of at least 2048 bits, SHA-256, `digitalSignature` and `contentCommitment`, `clientAuth` and `emailProtection`, country `BR`, and a policy OID under `2.16.76.1.2.1.n`. A3 and A4 keys live on a cryptographic device and generally cannot be exported into KV, so this demo is the A1 profile only.

The CPF otherName uses OID `2.16.76.1.3.1`, which is the right identifier, but the laboratory value is a UTF-8 string. An accredited certificate encodes that attribute as the fixed octet string defined in DOC-ICP-04. The person and the CPF `111.444.777-35` are fictitious.

The Podman stack runs Vault in dev mode with the root token `root`. Terraform state for this lab contains the service CA private keys, the ICP-Brasil leaf private key, the AppRole secret id, and the database password. `deploy/icp/private_key.pem` is the same laboratory leaf key and is in the repository so `terraform apply` works after a clone. State is gitignored. Do not point the lab script at a production Vault, and do not install these CAs in a production trust store.

## Layout

```text
app/                  Python UI and Containerfile
terraform/            Vault PKI, KV secret for the ICP-Brasil certificate, database engine, AppRole, optional Kubernetes auth
deploy/agent/         Vault Agent configuration and templates
deploy/icp/           Laboratory ICP-Brasil certificate, leaf keys, and issuing CA
deploy/podman/        Compose lab, including a dev-mode Vault
deploy/nomad/         PostgreSQL job and application job
deploy/kubernetes/    Namespace, PostgreSQL, and Vault Secrets Operator resources
deploy/postgres/      Demo table
scripts/podman-lab.sh           Starts the Podman lab, then applies Terraform
scripts/podman-teardown.sh      Stops that lab and removes its local state
scripts/kubernetes-lab.sh       Deploys the lab on Kubernetes, then applies Terraform
scripts/kubernetes-teardown.sh  Removes that lab and, when Vault env is set, its Vault config
scripts/nomad-lab.sh            Deploys the lab on Nomad, then applies Terraform
scripts/nomad-teardown.sh       Removes that lab and, when Vault env is set, its Vault config
```

The rendered files, on every runtime, are:

```text
db.json     username, password, and (from Agent or Nomad) the lease
tls.json    service certificate, private key, and issuing CA
icp.json    ICP-Brasil certificate, public key, private key, issuing CA, and CA chain
```

## Podman

Requires Podman (or Docker Compose), Terraform 1.10 or newer, curl, and Python 3.

```bash
./scripts/podman-lab.sh
```

When `VAULT_ADDR` and `VAULT_TOKEN` are set, the script uses that Vault and does not start one. `VAULT_SKIP_VERIFY=true` skips TLS verification for Terraform, curl, and Vault Agent. A loopback address is rewritten to `host.containers.internal` (Podman) or `host.docker.internal` (Docker) for the agent container. PostgreSQL still starts here and is published on port 5432. When `VAULT_ADDR` is on localhost, Vault is given `127.0.0.1` for that database, because the Compose name `postgres` is not visible outside the lab network. Set `TF_VAR_postgres_host` when Vault runs somewhere else.

Terraform creates a Vault namespace named `demo` (override with `vault_namespace` or `TF_VAR_vault_namespace`) and configures every mount, policy, and auth method inside it. `VAULT_NAMESPACE`, when set, is the parent. Vault Agent logs in to that namespace. This requires Vault Enterprise or HCP Vault.

When those variables are unset, the script starts a dev-mode Vault on http://127.0.0.1:8200 with the token `root` and checks that port 8200 is that container before it applies Terraform.

The script then writes the AppRole files and starts Vault Agent and the application.

Stop it with the same `VAULT_ADDR`, `VAULT_TOKEN`, and `VAULT_SKIP_VERIFY`:

```bash
./scripts/podman-teardown.sh
```

Teardown runs `terraform destroy` against that Vault, which deletes the lab namespace and everything inside it, then removes the Compose project `vault-pki-demo` (containers, network, rendered volume, and the locally built app image), the AppRole files under `deploy/podman/secrets/`, and `terraform/terraform.tfstate`. The Vault server stays up. Pulled images stay. If you started the lab with a different `COMPOSE_PROJECT_NAME`, set the same value for teardown. Without `VAULT_ADDR`, teardown only removes the local dev Vault and its state.

- UI: http://127.0.0.1:8080
- HTTPS, using the rendered service certificate: https://127.0.0.1:8443
- Vault: the `VAULT_ADDR` you set, or http://127.0.0.1:8200 (token `root`) when it is unset

The browser will warn about the lab CA. The service card has a link to download the issuing CA. Trust it only in a lab profile if you want the warning to go away. `localhost` is on the certificate.

The bundled dev-mode Vault keeps nothing on disk. If you recreate that container, run `./scripts/podman-teardown.sh` (or delete `terraform/terraform.tfstate`) and start again.

To do the same steps by hand:

```bash
podman compose -f deploy/podman/compose.yaml up -d vault postgres
export VAULT_ADDR=http://127.0.0.1:8200
export VAULT_TOKEN=root
terraform -chdir=terraform init
terraform -chdir=terraform apply
./scripts/write-approle-files.sh
podman compose -f deploy/podman/compose.yaml up -d --build vault-agent app
```

`deploy/podman/lab.env` and the Terraform defaults use the database user `vault` and the password `vault-lab-password`. Vault reaches PostgreSQL at the compose name `postgres`. The application does too. Those are not the dynamic credentials; Vault creates those on request.

## What the page is showing

The A1 card reads the KV secret and checks the profile above: key size, signature, key usage, extended key usage, country, policy arc, CPF OID, one-year maximum, `CA:FALSE`, and that the stored public key matches the certificate. The service card is a different chain (`Vault Demo Root CA` / `Vault Demo Intermediate CA`) with `serverAuth`, issued by the PKI engine. The database card logs in with the rendered role and reads `registros`. The password and the private keys are not included in `/api/status`.

To show rotation, revoke the lease printed on the database card:

```bash
export VAULT_ADDR=http://127.0.0.1:8200
export VAULT_TOKEN=root
vault lease revoke -namespace=demo database/creds/demo-app/<lease-id>
```

Vault Agent renders a new role within a few seconds. The username on the page changes without a restart. The service certificate is issued for 1 minute. The page polls that certificate and replaces only the service PKI card when a new one is rendered. That card turns yellow for the last 10 seconds of the certificate, then green when the next one is rendered. The PostgreSQL credential lasts 2 minutes. The page polls that credential and replaces only the database card when a new role is rendered. That card turns yellow for the last 10 seconds, then returns to amber. The ICP-Brasil certificate has no lease. Update the KV secret (or replace `deploy/icp/` and apply Terraform); Agent, Nomad, and the Secrets Operator re-read it and replace `icp.json`.

## Terraform

`terraform/` expects `VAULT_ADDR` and `VAULT_TOKEN`. It creates a namespace, then creates the following inside it:

- `pki_root` and `pki_int`, role `demo-server`, for service TLS
- a KV v2 mount `kv` and the secret `icp-brasil`, loaded from `deploy/icp/` (override the file paths with `icp_certificate_file`, `icp_private_key_file`, `icp_public_key_file`, `icp_issuing_ca_file`, and `icp_ca_chain_file`). Custom metadata on that secret holds the common name, issuer, serial, validity, fingerprint, and policy OID
- a database mount, a PostgreSQL connection, and the role `demo-app`
- the policy `demo-app` and an AppRole of the same name
- the policy `icp-metadata-reader`, which can list `kv/metadata/` and read `kv/metadata/icp-brasil`, and cannot read `kv/data/icp-brasil`
- the Kubernetes auth method only when `enable_kubernetes_auth` is true

`postgres_host` is the address **Vault** uses to open PostgreSQL, which is not always the address the application uses.

```bash
export VAULT_ADDR=https://vault.example:8200
export VAULT_TOKEN=...
terraform -chdir=terraform apply \
  -var='postgres_host=postgres.example' \
  -var='vault_address=https://vault.example:8200'
```

See `terraform/terraform.tfvars.example`. An existing `auth/approle` mount can be imported instead of created:

```bash
terraform -chdir=terraform import vault_auth_backend.approle auth/approle
```

State holds the service CA private keys and the ICP-Brasil leaf private key. Keep it accordingly.

## Nomad

Requires Nomad, Terraform, Python 3, curl, and either Podman or Docker. `VAULT_ADDR` and `VAULT_TOKEN` must already point at Vault. `VAULT_SKIP_VERIFY=true` skips TLS verification for Terraform.

```bash
./scripts/nomad-lab.sh
./scripts/nomad-teardown.sh
```

The script builds `vault-pki-icp-brasil-demo:local`, starts PostgreSQL, applies Terraform, then starts the demo job. Both jobs use host networking and datacenter `dc1`, and they expect to land on the same client so the application can open PostgreSQL at `127.0.0.1:5432`. When Vault is on localhost, Terraform uses that address too. When Vault is elsewhere, set `TF_VAR_postgres_host` to the Nomad client address Vault can open.

The Nomad client needs a `vault` stanza whose token can create a child token with the `demo-app` policy in the Vault namespace `demo`. On a cluster that only accepts workload identity, change the job's `vault` block to `role = "demo-app"` and bind that role to the job identity. The job's `namespace` must stay `demo`. The client must be able to run the image the script built. Templates use `change_mode = "noop"` because the application re-reads the files.

Teardown stops and purges `vault-pki-demo` and `vault-pki-demo-db`. It force-revokes database leases and runs `terraform destroy` when `VAULT_ADDR` and `VAULT_TOKEN` are set. The Vault server and the Nomad agent stay running. If destroy fails, the jobs are still removed and Terraform state is kept.

## Kubernetes and the Vault Secrets Operator

Requires kubectl, Terraform, Python 3, curl, OpenSSL, and either Podman or Docker. Helm is required only when the Vault Secrets Operator is not already installed. `VAULT_ADDR` and `VAULT_TOKEN` must already point at Vault. `VAULT_SKIP_VERIFY=true` skips TLS verification for Terraform and sets `skipTLSVerify` on the operator connection.

```bash
./scripts/kubernetes-lab.sh
./scripts/kubernetes-teardown.sh
```

The script builds `vault-pki-icp-brasil-demo:local` and loads it into a kind or minikube cluster when that context is current. It installs the operator if the `VaultConnection` CRD is missing, starts PostgreSQL and the token reviewer, then applies Terraform with Kubernetes auth enabled. The reviewer token lasts 24 hours. When Vault is a pod in this cluster, `kubernetes_host` is `https://kubernetes.default.svc`, because the kubeconfig address is on this machine and is not the API server from inside the pod. Set `TF_VAR_kubernetes_host` to choose another API address.

When `VAULT_ADDR` is a loopback address published by the current cluster node, as with minikube or kind, Vault is inside that node. Terraform then uses `postgres.vault-demo.svc.cluster.local`, and the operator uses the in-cluster Service that owns the published port. A forward to `127.0.0.1` on this machine is not reachable from that Vault. When the `vault` binary itself is listening on this machine, the script forwards PostgreSQL to `127.0.0.1:15432` instead. Set `KUBERNETES_POSTGRES_PORT` to choose another local port, or set `TF_VAR_postgres_host` to choose the address yourself. The application uses the short name `postgres`.

Set `KUBERNETES_VAULT_ADDRESS` when the operator pods need a Vault URL other than the one the script selects. The operator writes `db.json`, `tls.json`, and `icp.json` into Kubernetes Secrets. The pod mounts them at `/vault/secrets`. The Vault role audience and the `VaultAuth` audience are both `vault`. `VaultAuth` and the secret resources set the Vault namespace to `demo`, matching `vault_namespace`.

The application Service is a NodePort. It listens on port 8085 inside the cluster and on node port 30085. Set `APP_PORT` or `APP_NODE_PORT` to choose other ports. When the node address is not routed to this machine, the script publishes node port 30085 on `http://127.0.0.1:8085`. Open that address in a browser. Teardown removes the publisher with the Service.

Teardown deletes the `deploy/kubernetes` resources, including the namespace and the cluster-scoped token reviewer binding. It force-revokes database leases and runs `terraform destroy` when `VAULT_ADDR` and `VAULT_TOKEN` are set. The Vault server and the operator stay installed. If destroy fails, the Kubernetes resources are still removed and Terraform state is kept.

## Tests

```bash
python3 -m venv .venv
.venv/bin/pip install -r app/requirements.txt
PYTHONPATH=app .venv/bin/python -m unittest discover -s app/tests
terraform -chdir=terraform fmt -check -recursive
terraform -chdir=terraform init -backend=false
terraform -chdir=terraform validate
```

`validate` does not need a running Vault. `apply` does, and the database connection is verified against PostgreSQL.
